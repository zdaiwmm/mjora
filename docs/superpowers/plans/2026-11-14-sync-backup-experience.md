# mjora 照片同步与备份体验实施方案

日期：2026 年 11 月 14 日。状态：待实施方案，本文件不代表功能已经修复或发布。

目标：解决删除后的错误提示、网页新增照片无法打开、缺少清理保留时间、缩略图模糊、照片与相册数量混淆、备份页未简化，以及每次进入 App 重复全量匹配七个问题。

实施基线：iOS 仓库 `imora-native`，提交 `eb98070`；服务端及 Web 仓库 `mjora-server`，提交 `6a960dbe6`。最新安装记录已更新为 iOS 1.0.1 构建 3，时间为北京时间 20:14；无线更新入口已经存在。本次不重复开发更新系统。服务端现有 Immich 3.4.1，已上线的 Web 重连修复不能视为本次新增照片点击问题已经解决。

## 一 选定实施路线

采用现有原生 App 和现有服务端，补齐增量同步、独立的删除状态，以及两端一致的展示与操作。服务端已有 `/sync/stream` 和会话级同步确认接口，优先复用，不新增上传代理、不改数据库结构、不升级 Immich 主版本。Web 修复随现有照片服务镜像发布。

比较过两条可行路线：

| 路线 | 收益 | 成本及限制 | 本次选择 |
| --- | --- | --- | --- |
| 继续使用现有 REST 匹配，增加缓存、节流和定期全量核验 | 改动较少，适合先修重复触发 | 断线后仍需要全量核对才能可靠发现漏掉的云端删除，难以彻底消除大图库逐张请求 | 作为旧服务端或 API Key 登录的兼容路径 |
| PhotoKit 持久变更记录加 Immich 增量同步 | 跨启动只处理变化，可补回离线期间删除，降低逐张请求 | 需要处理同步确认、缓存事务、重放和重置 | 当前家庭服务器使用此路线 |

以下数字属于本方案的验收目标，不是现有版本测量结果。七项问题中，重复全量匹配、删除状态分类、清理选项缺失和相册数量含义已有源码依据；网页点击和具体模糊图片的根因须先复现，不能仅改候选代码后宣称修复。

## 二 用户最终看到的行为

| 场景 | 修改后的行为 |
| --- | --- |
| 正常进入或返回 App | 先显示已有照片；无变化时不重新核对五千张照片，不出现重复的全量进度 |
| 新拍、编辑或删除手机照片 | 只更新涉及的本机项目；新增照片进入待备份队列，原有已备份状态不整体归零 |
| 网页删除云端照片 | 云端照片列表移除；本机原片继续保留。它在本机列表标为“云端已删除”，不报普通备份失败、不自动传回服务器 |
| 恢复云端回收站照片 | 增量同步恢复云端显示；核对照片身份后更新关联，清掉对应删除状态 |
| 网页停留照片页期间发生新上传 | 新缩略图出现后立即可打开；关闭查看器后，其他照片仍可连续打开 |
| 缩略图清晰图暂未到达 | 可以短暂显示预览；超时切换可用来源，失败显示重试入口，不无限停留在模糊图 |
| 查找所有备份照片 | “照片”页默认显示云端照片，顶部可切换“云端／本机”；相册页另设“全部云端照片”入口 |
| 查看“最近项目” | 保留原相册及名称，显示真实成员数；不会把它误当成整个备份图库，也不会自动塞入所有照片 |
| 日常使用备份页 | 一个主开关“自动备份”，配合明确的进度、当前连接和必要的暂停原因；手动工具放到高级选项 |
| 清理设备 | 可选择保留最近多久、收藏和指定本机相册；先扫描预览，再核验并确认清理 |

“实时”定义为：两端在线、App 在前台、服务器处理完成时，事件驱动更新；在受控局域网测试中以 3 秒内反映变更为目标。App 被 iOS 挂起或终止时，下次获得执行机会后补齐变化，不承诺熄屏后界面仍持续运行。

## 三 同步状态与增量引擎

### 3.1 区分展示状态与删除许可

保留现有 `BackupProof` 的会话及资源校验约束。新增持久的历史状态供界面和统计使用，不能拿历史状态直接授权删除手机文件。

| 状态 | 展示及统计 | 自动上传 | 清理设备 |
| --- | --- | --- | --- |
| 本机待备份 | 计入待备份 | 按策略上传 | 不允许 |
| 已备份或云端已确认存在 | 显示已备份；离线时注明状态更新时间 | 不重复上传 | 仍须重新核验原件 |
| 云端已删除或在回收站 | 本机列表灰色提示，单独计数 | 禁止自动重传 | 不允许 |
| 待核验或连接中断 | 保留上次已知状态，并显示连接状态 | 不因为请求失败就把已知照片重新上传 | 不允许 |
| 真实上传失败 | 显示具体原因，达到阈值后进入失败列表 | 按现有重试策略处理 | 不允许 |

已有“云端删除禁止重传”标记继续沿用；仅将它从普通失败、待上传和反复提醒中分离。账户切换、云端事件、资源变化都必须能使相关的最新校验证据失效。

### 3.2 本机增量扫描

首次建立本机元数据快照，并保存 PhotoKit 持久变更 token。后续通过 `fetchPersistentChanges(since:)` 获取新增、修改和删除标识，仅重新读取相关元数据；原图哈希只针对确实新增或内容修订变化的资源。

首次快照必须先捕获扫描边界 token，再扫描，随后消费该边界以来的变化并更新快照；快照与实际已消费到的 token 在同一事务保存。禁止扫描结束后直接保存最新 token，否则会漏掉扫描期间变化。扫描、应用变化或事务提交前崩溃均从上次已提交边界恢复。token 失效、权限范围变化或快照损坏时，仅执行一次本机元数据重扫；重扫本身不等于给全部原图重新算哈希，也不等于重传。无法证明资源未变化的项目维持现有保守校验。

同一时刻只允许一个扫描任务，时间线、备份页和前台恢复共享它。完成已有数据库迁移或一次性基线后，后续冷启动也使用持久 token。

### 3.3 云端增量同步

新增会话级 `RemoteSyncClient`，按当前 Immich 3.4.1 的实际协议消费 JSON Lines。基础订阅为 `AssetsV2`、`AlbumsV2`、`AlbumToAssetsV1`；伙伴及共享照片沿用原浏览权限路径，不并入“本机备份完成数”，需要补订阅时仍按独立权限范围处理。

消费照片新增、修改、软删除、永久删除，以及相册成员变化。检查照片归属、校验值和 Live Photo 双资源关联。流中的资料足以更新历史存在状态；上传后的首次成功核验以及设备清理仍使用现有严格核验路径。

使用系统 SQLite3 新增 `SyncStateStore`，保存本机快照、云端快照、删除标记、待处理变化和同步进度；现有备份索引 JSON 继续保存哈希与上传证据，本次不整体替换。历史配对、资源校验值、删除保护按固定服务器身份和账号保存，同账号重新登录仍保留；仅云端同步 checkpoint 按登录会话隔离，LAN/WAN 地址切换仍属于同一账号空间。

`loginSessionKey` 随登录凭证持久保存：新登录创建、冷启动复用、退出后重新登录才更换；HTTP 同步确认由该凭证对应的服务端会话承接。不能使用每次启动生成的 `client.context.id` 充当持久会话标识，它只用于拒绝过期异步结果。

必须实现：

- 每批云端变化先在 SQLite 事务落盘，并保存待应用到现有备份索引的操作；随后幂等更新 BackupIndex 并确认 JSON flush 成功，再清理待应用操作，最后向 `/sync/ack` 提交服务器返回的确认标识。SQLite 与 JSON 不假设跨文件事务。任一步失败均不确认该批，也不放行依赖该批删除状态的上传；不自行构造确认值。
- 网络中断或确认失败允许重放，同一事件重复应用结果不变。启动时先恢复持久的待应用操作，再运行自动备份；上传最后交接同时受持久删除标记约束。不同登录会话不共享确认进度。
- 本地快照丢失但服务器已有确认进度时，重建当前 App 会话的同步基线；不能跳到旧确认位置后漏掉历史项目。旧 JSON 的账号历史配对与删除保护在重建中保留，不随派生缓存一起清空；若两者同时损坏则先暂停自动上传，不能把未知历史当成从未备份。
- 收到 `SyncResetV1` 时按现有服务端 reset 确认握手重建；仅在完整基线与 `SyncCompleteV1` 落盘后替换正式快照。半条流不能被当成完整图库。当前服务端超过 30 天的同步进度会触发 reset，不能假设永久删除历史还可重放。完整重建必须比较同账号历史配对：以前已关联但新完整基线中缺失的资源，转成云端删除保护并写回旧索引；Live Photo 的任一必要组件缺失都保护整个照片。
- 云端恢复补齐完成后，再允许那些依赖“云端不存在”的自动上传判定，避免断线期间已删除的照片被误传回去。
- 解析器必须支持半行和多行网络分块，单记录上限 256 KiB；超限或未知关键记录停止本轮并保留旧快照，不丢弃数据后继续确认。
- API Key 登录不能使用当前会话同步接口；不支持的服务端走兼容 REST 路径。超时或证书失败不伪装为“不支持增量同步”。

兼容路径在一次前台恢复中最多运行一次受控全量核对。其无逐张请求的目标不适用，界面明确显示“正在核对旧版服务端”。当前家庭服务器必须通过增量协议验收后才能宣称解决反复全量匹配。

### 3.4 合并触发

新增 `BackupReconcileCoordinator`，统一处理前台恢复、PhotoKit 变化、Socket 恢复、云端变化、手动操作和恢复任务。

一个账号仅一个运行实例；触发时记录尚未覆盖的变化，不因重复“已连接”事件设置全量重跑。运行期间收到真实新变化则并入队列，必要时补处理涉及的项目。已有健康上传不因切回前台而取消。重连只触发增量拉取，不再次清空全图库证明。

新增 `canSkipRoutineBackupRecheck` 判定，要求同账号、资源修订未变、云端完整基线有效、最近一次增量补齐完成且该项目未被标为待核验；云端删除保护优先于所有其他判定。将近期捕获检查、主上传计划、恢复任务中“是否还需要匹配／上传”的调用点迁移到此判定，不能继续只依赖会话级 `isBackedUp`。历史备份统计使用独立展示投影，设备清理仍只接受当次严格证明。

## 四 删除同步与失败提醒

云端永久删除或进入回收站时，在同一状态更新中完成：更新删除标记、移除云端时间线条目、清掉相关图片来源关联、撤销清理资格、取消尚未发出的上传、移出普通失败账本并更新统计。

已发出的上传回执不能覆盖后发生的删除标记；乱序事件没有可靠版本时，保持删除保护，等待一次权威增量结果确认恢复。恢复回收站项目或用户在明确提示后选择“重新备份”才允许解除对应保护。

“重新备份”放在该照片的详情操作中，展示其将重新创建云端副本。手机原片的删除仍只通过明确的本机清理流程发生。

单次缩略图 404 不直接判为用户删除：先标记媒体不可用并针对该照片核验；401、403、离线、超时分别显示登录、权限或网络状态，不给五千张照片逐张累计上传失败。

## 五 网页新增照片点击与坏图

先用合成数据固定复现场景：打开照片页不刷新，后台注入一张上传完成照片，等缩略图出现，点击打开、返回，再连续打开另一张新照片和旧照片。分别覆盖现有日期、新日期、新月份、虚拟列表离屏后滚回，以及同图重复事件。

观测 DOM 命中元素、点击回调、目标照片 ID、路由、详情接口响应和查看器打开状态，区分事件未触发、路由未切换、接口失败、查看器遮挡或列表成员缺失。修复落在首个断开的环节。

需要检查的现有实现包括：Socket 待处理批次、时间线 upsert/remove、月日分组及计数、查看器当前成员、查询缓存失效和关闭后的交互层。删除与延迟上传事件冲突按照片版本及删除保护处理；断开订阅时取消旧节流任务，防止旧账号或旧页面的事件回写。

如服务器照片记录仍在但缩略图请求失败，应展示可点击的处理中或重试状态；确认已删除后才移除条目。确实需要重建衍生图时，只对确认受影响的项目重新执行缩略图任务，不全库重建、不碰原图。若必须修改服务端任务逻辑，作为复现结果驱动的单独修复，不扩大为服务端升级。

## 六 缩略图清晰度与重试

采用有界的渐进加载：先画缓存或低清预览，再请求目标像素的清晰图；已配对照片优先本机可用清晰图，2 秒内只得到低清结果时并行尝试服务器缩略图。服务器缩略图分辨率不足时，至多升级请求一次 `preview`，不在网格拉取原图或视频。

本机照片未备份且高清资源在 iCloud 时，保留预览并给出明确加载或重试状态，不为整个屏幕自动导出所有原图。请求失败显示轻量重试入口；回到前台可对当前屏幕失败项恢复一次，不启动全库匹配。错误不能永久缓存为成功结果。

低清预览与最终图分开缓存，使用账号、资源版本、来源规格和目标像素作为缓存键。原图本来就小的照片不循环升级。加载并发上限 4，只预取当前屏及前后各一屏；沿用现有内存上限，图片离屏后取消未完成请求。

## 七 照片入口与备份页

### 7.1 照片与相册

“照片”页默认“云端”，另可切换“本机”，并记住上次选择。“云端”显示同账号正常可见的服务器时间线，“本机”显示有权限读取的手机照片及备份状态。回收站、归档与锁定项目继续保留各自入口。

相册页顶部新增“全部云端照片”虚拟入口，复用时间线，不创建服务器相册，不写入五千条相册成员关系。“最近项目”保持其实际相册身份。

分别提供“云端照片项目数”“本机已备份项目数”“待备份项目数”“云端已删除项目数”。Live Photo 按一个照片项目统计，照片与视频组件不重复计算；共享照片和其他设备照片不计入本机备份完成数。堆叠、归档及当前筛选影响列表数量时，计数必须使用同一筛选口径。

### 7.2 备份页布局

| 位置 | 展示内容与操作 |
| --- | --- |
| 页面顶部 | “自动备份”主开关；关闭仅关闭自动任务，普通浏览仍正常同步 |
| 状态卡片 | 已备份、待备份、处理中、云端已删除；阶段、当前文件与实际传输速度 |
| 连接状态 | “当前使用局域网／外网／离线”；自动选择已验证的局域网，正常使用不要求每次手动选 |
| 条件与异常 | 网络、低电量、系统暂停等真实原因；可恢复时仅展示一个“继续备份”操作 |
| 存储操作 | “清理设备”，进入独立配置与预览页 |
| 高级选项 | 立即备份、保持前台备份、连接方式、截图与大小限制、电量策略、诊断与重新完整核验 |

复用现有后台恢复与长任务能力，不以 UI 简化为由合并含义不同的系统 API。日常自动备份无需每次确认；需要用户发起的长时间继续任务由“继续备份”触发。系统拒绝或暂停时显示实际状态，保留任务进度；不承诺后台永不停止。

手动“仅局域网”仍保留在高级连接方式中，失败时保持暂停，不偷偷切外网。自动模式使用现有已验证路由策略；切换路由不更换账号、不清空索引。

### 7.3 版本可见性

沿用“关于与更新”，显示实际安装版本、构建号、最近更新说明及更新检查结果。下一个修复候选建议使用 1.0.2，构建号在打包时读取当前已发布和已准备版本的最大值后递增。安装后核对主 App、分享扩展、更新服务与实际安装回执一致，不以“代码已推送”代替安装完成。

## 八 清理设备的保留策略

提供“保留最近 7／30／90／180／365 天”“自定义保留起始日期”“不按时间保留”。默认最近 30 天；默认保留收藏，支持选择保留指定本机相册中的照片与视频。

“最近 N 天”按预览时设备时区的自然日计算，含今天：截止时间为今天零点向前 N−1 天。仅 creationDate 严格早于截止时间的项目进入候选。日期未知、收藏、受保护相册成员、未成功备份、云端已删除、Live Photo 资源不完整的项目均保留。

预览显示绝对日期范围、待清理照片和视频数、预计释放空间，以及按近期、收藏、指定相册、未验证等原因保留的数量。一个项目可能有多个保留原因，合计保留数按项目去重。

将截止时间、时区、保护选项与相册标识集合绑定到不可变 `CleanupReport`；改变配置即废弃旧预览。确认时重新核对当前项目修订、收藏状态及受保护相册成员，配置或资格改变则停止并要求重新扫描。继续执行现有服务器元数据、双资源校验、原件完整读取与最终 PhotoKit 提交校验，不降低现有门槛。

清理页写明：若开启 iCloud 照片，系统删除会同步到 iCloud 和同账号设备；释放空间以系统最近删除中的处理结果为准。这里只手动确认清理，不增加自动删除照片任务。详情页明确选择“移除本机副本”的独立操作仍沿用自己的确认范围，不悄悄套用批量保留时间。

## 十一 发布顺序与回滚

开发顺序为 T1 → T2 → T3 → T5／T6／T7 → T8；T4 可在独立 Web 仓库并行进行。展示与清理都依赖新的状态定义，不能抢先把历史备份标记当成可删除许可。

Web 精确复现和回归完成后可先单独发布；只更新现有照片服务镜像，保留当前 Compose 覆盖文件、镜像标签和原回滚路径，不重启数据库、Redis、机器学习服务或整台主机。App 在原设备上覆盖安装，不卸载重装。

增量数据库为新增的派生缓存，升级迁移保留旧索引；不把旧 JSON 改成旧版无法读取的格式。新模式有独立开关，协议失败可以暂停并保留快照；需要回滚时回到现有受控 REST 匹配，而不是丢索引后重传。回滚前必须将派生缓存中的待应用删除标记写回旧索引并完成 flush；无法完成时保持自动上传暂停，不能直接切旧版后放行上传。回滚仍须保留云端删除防重传标记。

发布记录必须包含 App 实际版本与构建、源码提交、Web 镜像标识、验证结果，以及已安装源码对应的自动续签固定版本。线上观察只在获准范围内检查服务健康和必要汇总，不为了复现而操作用户真实照片。
