# Batch 2 stage 1

The local change adds an explicit On Device search action, permission-scoped search publication, read-only photo edit target binding, and isolated background acceptance tools. It does not enable two-target saves, an edit outbox, local OCR, place indexing, or new backup/delete eligibility.

The changes were rebased without conflicts onto client main `4454973b20c64d085b7456af02f97bbc0d64e0d4`. Server main `4c6d02652f60aff35f62ba7edf3d02750471be04` was reviewed and was not modified. The earlier isolated-base results are retained as history; the integrated candidate has its own evidence.

## Search

Normal Search continues to use Cloud Photos. The On Device library menu has an explicit Search On Device action. Typed requests carry their source and identity. Metadata loading and query results are fenced by session, permission generation, request generation, and a fresh PhotoKit visible-ID lookup. Hidden and revoked assets cannot be published from an earlier result.

The existing filename/date matching remains metadata-only. This stage adds no persistent index or image recognition. Existing English and Simplified Chinese strings are reused.

## Edit target binding

`PhotoEditTargetResolver` and its reader return local/cloud/both target identities, independent baselines, and typed unavailability reasons. Only an explicit cross-target preflight reads both originals. It compares streamed SHA-256, byte count, upright dimensions and orientation. The cloud original must also match its authoritative SHA-1 and use `edited=false` with the edit-input file role.

Account, server, session, access, PIN, recipe and source changes invalidate the result. A preview or retained playback file cannot supply original-input proof. Existing PhotoKit saves and draft v1 remain unchanged. A resolved baseline is not a server CAS token or backup deletion proof.

## Background tools

`tests/integration/background-validation/` contains the explicit-revision source exporter, compile-gated transport panel, synthetic MP4 generator, fixed-target ciphertext relay, persistent run ledger and evidence checker. Preparation requires the requested revision to match current HEAD. Candidate identifiers, App Group and Keychain service are isolated; the normal AppDelegate and SessionStore remain in place.

The ledger persists intent before external writes and records an acknowledged staging reference before proceeding. Asset deletion requires an observed `created` receipt and authenticated owner/run-name/original-digest verification. A duplicate without durable creation provenance remains manual recovery. A staging reference alone never grants asset deletion authority.

The checker validates forward progress, received part coverage, the authenticated offset before any post-drop upload, original readback and cleanup receipts. It never emits product PASS. Stable lock evidence still requires at least 1,800 seconds. The transport panel cannot manufacture PhotoKit/BackupManager pipeline evidence.
